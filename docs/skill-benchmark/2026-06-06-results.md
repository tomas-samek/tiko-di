## Fairness disclosure

This benchmark uses a multi-service event-driven app with compile-time
topology validation as the test problem. **That is deliberately
tiko-di's claimed home turf.** The orchestrator model exists to make
this exact shape pleasant to build; choosing it for the bench plays to
that strength.

The question being tested is therefore **not** "is tiko-di competitive
on arbitrary tasks?" It is much narrower:

> Does the `tiko-build` skill close the training-data gap between
> tiko-di and mainstream frameworks **on tiko's home turf**?

That is the only claim a reader should draw from any number in this
report. Tiko-di on Spring Data magic, on full observability stack, on
migration-flavoured tasks — those are out of scope and would have a
different bench.

For the same reason, the cross-framework cells (Spring Boot / Micronaut
/ Quarkus) are present as a **floor reference**, not a competitive
claim. They establish "this is what mainstream-trained agents produce
on the same problem when handed an ecosystem they have rich training
data on." The tiko cells are then read against that floor: with-skill
vs without-skill is the load-bearing comparison.

## Methodology

- **Prompts:** `prompt-lean.md` and `prompt-specified.md` in this
  directory, locked at first commit. Never edited mid-run.
- **Rubric:** `rubric.md` in this directory, also locked. Scored as a
  16-vector per cell, not just a total.
- **Matrix:** framework × prompt-variant × agent × run-id.
  - **Frameworks:** tiko-di (with skill), tiko-di (without skill),
    Spring Boot, Micronaut. Optional: Quarkus.
  - **Agents:** at least two — picked per cost budget. List the
    specific model id and skill-loading mechanism in the "agent"
    column.
  - **Prompt variants:** lean, specified.
  - **Runs per cell:** ≥ 3 to smooth single-shot noise.
- **Per-run metrics:** tokens in, tokens out, wall-time, compile-on-
  first-attempt (yes/no), correction-turns to working binary (capped
  at 5 — anything past 5 is recorded as `>5` and the run is marked
  failed), rubric vector + total, link to transcript, link to produced
  source tree (gist or branch).
- **Harness script:** `scripts/run-benchmark.ps1` (PowerShell) and
  `scripts/run-benchmark.sh` (bash) automate the `mvn verify` capture
  and emit a row template. The agent-invocation half is manual — each
  agent has its own UI and that part doesn't script cleanly.

### Skill-loading mechanism — what counts as "with skill"

The tiko+skill vs tiko-noskill axis is the load-bearing comparison of
the whole benchmark, so what counts as each side is a methodology rule,
not a freetext convention.

**With skill** (any one of the following is sufficient — record which
in the agent column):

- **auto-loaded.** Agent runs on a project tree that contains
  `.ai-skills/tiko-build/SKILL.md` and an agent-config file (`CLAUDE.md`
  / `AGENTS.md` / `.cursor/rules/tiko.md` / etc.) that points at it,
  and the agent's transcript shows it actually opened the file.
- **system-prompt-pasted.** The full text of `SKILL.md` is in the
  agent's system prompt or initial context.
- **url-fetched.** The agent fetches the GitHub-hosted SKILL.md via
  WebFetch / browse equivalent and reads it before generating code.

**Without skill** (any one of the following is sufficient):

- **scrubbed project.** Before the agent run, delete `.ai-skills/` and
  the skill-pointer blocks from the agent-config files in the
  scaffolded project. Document the deletion in the transcript link.
- **fresh-without.** Agent runs entirely outside a tiko project tree —
  the prompt + agent's training data are the only inputs. The agent
  reads no tiko-side documentation during the run.

**"With access but did not invoke" is recorded as without-skill.** If
the SKILL.md file was on disk but the agent's transcript shows it never
opened it, score the cell as no-skill and mark the agent column
`with-skill (not invoked)`. The point is to measure whether the skill
helps when read, not whether it sits on disk.

### Per-run state isolation

- **Fresh context.** Every run starts a new agent session — no
  conversation history from a previous run is reused.
- **Fresh project tree.** Each run scaffolds a brand-new directory
  from the archetype. Do not reuse a partially-built workspace from a
  prior run, even within the same cell.
- **Fresh local Maven cache: not required.** The archetype itself
  pulls deterministic versions; cache reuse across runs is acceptable
  and saves time.

### "Without-skill" tiko cell — practical mechanics

A freshly scaffolded tiko project now ships
`.ai-skills/tiko-build/SKILL.md` and matching agent-config blocks. So
"without skill" needs an active removal step, not just "the agent
didn't ask for help."

Two reproducible approaches:

1. **Scrub after scaffold.** Run the archetype; immediately delete
   `.ai-skills/`, and delete the "Building a service" pointer blocks
   in `CLAUDE.md` and `AGENTS.md`. Commit the scrubbed state to a
   throwaway branch so the agent's starting state is publicly visible.
2. **Pre-0.1.0-scaffold archive.** Pin a pre-skill version of the
   archetype output (or hand-construct an equivalent minimal tiko
   project) and serve that as the starting tree. Same effect, doesn't
   require deletion bookkeeping.

Either works; pick one and stick with it inside a result set.

## How to add a run, end-to-end

1. **Pick a cell.** Framework × prompt-variant × agent × run-id.
   Check the per-run table; if the cell already has runs, increment
   the run-id.
2. **Prepare the starting tree.**
   - **tiko + skill (auto-loaded):** `mvn archetype:generate` per
     README; do not delete `.ai-skills/`. Confirm the scaffolded tree
     contains `.ai-skills/tiko-build/SKILL.md` before the agent run.
   - **tiko + skill (system-prompt-pasted):** scaffold the project
     *without* `.ai-skills/` (delete after archetype) so the only
     skill source is the system prompt. Document the system prompt
     content in the transcript export.
   - **tiko + no skill:** scaffold, then `rm -rf .ai-skills` and edit
     `CLAUDE.md` + `AGENTS.md` to remove the pointer blocks. Commit
     the scrubbed tree to a throwaway branch so the agent's input
     state is visible.
   - **Spring Boot / Micronaut / Quarkus:** no scaffolding step — the
     agent uses the ecosystem's native init flow from the prompt.
3. **Paste the locked prompt.** Verbatim from `prompt-lean.md` or
   `prompt-specified.md`, with the cross-framework swap applied if
   needed. Do not paraphrase. Do not pre-clarify ambiguities.
4. **Run the agent end-to-end.** Let it scaffold, write services,
   declare done. Track correction turns per the rule above.
5. **Capture the build outcome.** Once the agent declares done, run:

   ```
   scripts/run-benchmark.ps1 -ProjectDir <path> -Cell "<name>" \
       -Prompt specified -Agent "<id @ date (loading-method)>" \
       -RunId <N> -Transcript <permanent-url> -Source <permanent-url>
   ```

   (or `.sh` on POSIX). Paste the emitted row template into the table
   below.
6. **Score the rubric.** Read the produced source, fill in the 16
   binary scores per `rubric.md`'s order, compute the total, paste
   into the rubric-vector and total columns.
7. **Permanence pass.** Make sure the transcript link is a saved
   export (not an ephemeral chat URL) and the source link is a gist
   or branch.

### Finding F1 — Prompt-coordinate / skill-release divergence

The locked specified prompt says:

> use tiko di framework, available on Maven Central as
> io.github.tomas-samek:tiko-*:0.1.0, including tiko-archetype for
> quick project startup.

A verbatim execution of that prompt today resolves the **0.1.0**
archetype from Maven Central. That archetype predates the
orchestrator-model skill (`.ai-skills/tiko-build/SKILL.md`) — the new
skill was added in `#266` and will first ship with **0.2.0**.

Smoke-test of the archetype output (2026-06-06, run-id 0 below)
confirms the scaffolded project contains the old `.ai-skills/SKILL.md`
(general "tiko-di exists" file with no orchestrator framing) but not
the new `.ai-skills/tiko-build/SKILL.md`. So an agent following the
verbatim prompt today gets a project tree that **does not satisfy the
"with-skill (auto-loaded)" definition** in the methodology section.

This means:

- **"tiko + skill (auto-loaded)" cells cannot be run truthfully
  against Central until 0.2.0 ships.** Until then, any with-skill run
  has to inject the skill out-of-band, which is a methodology variant
  (recorded below), not the headline cell type.
- **"tiko + no skill" cells via verbatim 0.1.0 prompt are runnable
  today** — the 0.1.0 archetype's bundled `SKILL.md` is general
  pointer text without orchestrator framing, so it functions as no
  skill for this benchmark's purposes.
- **"tiko + skill (system-prompt-pasted)" cells are runnable today** —
  the loading mechanism doesn't depend on what the archetype ships.
- **"tiko + skill (url-fetched)" cells are runnable today** —
  same reason; the skill's GitHub URL is the source.

### Interim variant for with-skill cells before 0.2.0 ships

Until the 0.2.0 archetype lands on Central, a "tiko + skill
(auto-loaded)" cell can be run with this documented deviation:

1. Run `mvn archetype:generate` with the prompt's verbatim 0.1.0
   coordinates.
2. **Before the agent run**, copy
   `.ai-skills/tiko-build/SKILL.md` from
   [the tiko-di repo at the matching commit] into the scaffolded
   project's `.ai-skills/` directory. Same for the agent-config
   pointer blocks in `CLAUDE.md` / `AGENTS.md` (add the
   "Building a service?" block from the archetype templates at the
   matching commit).
3. Record the cell as
   `tiko + skill (auto-loaded, manually injected pending 0.2.0)`.

Once 0.2.0 ships, repeat the previously-injected runs against the
clean Central artifact and compare. If the injection-method runs and
the Central-direct runs score within noise on the rubric, the
injection-method runs back-port cleanly.

### Recommendation

Sequence:

- Run **tiko + no skill** cells now (verbatim 0.1.0 prompt — runnable
  against Central today; data is publishable as-is).
- Run **tiko + skill (system-prompt-pasted)** cells now (loading
  mechanism independent of archetype release; data is publishable as-is).
- Defer **tiko + skill (auto-loaded)** cells against Central until
  0.2.0 ships, **or** run them with the documented injection variant
  above and a flag in the agent column.

This is the harness catching a real release-coordination dependency
before any data was recorded against a confused methodology. The
finding itself validates the harness more than a single dirty data
point would.

### Finding F2 — Published archetype lags the corrected skill (F1 redux)

Recorded while preparing the `tiko + skill (auto-loaded)` cell on
2026-06-20. `v0.3.0` was tagged **2026-06-18 09:02 UTC**; every
bundled-skill correction merged *after* it — #407 (`Scope.REQUEST` /
`@PostConstruct` fixes) at ~20:28 UTC the same evening, then #409 (full
canonical sync) and #410 (the #408 anti-drift gate) on 2026-06-19. So
`tiko-archetype:0.3.0` on Central — the only published version — bundles
the **pre-fix, drifted** `tiko-build` skill. A clean "auto-loaded from
Central" cell today would test the *wrong* skill.

This is structurally identical to F1: the headline auto-loaded cell is
not truthfully runnable against Central until the next release ships the
corrected archetype. Workaround used for run 1 (cleaner than F1's manual
injection): build `0.4.0-SNAPSHOT` and `mvn install` it to the local
`.m2`, then scaffold from `tiko-archetype:0.4.0-SNAPSHOT`. The installed
archetype's bundled `SKILL.md` was verified as the corrected one (275
lines, zero `Scope.REQUEST`) before the agent run, and the #408 gate
guarantees `bundled == canonical` on `main`. Agent column records the
local-`.m2` SNAPSHOT origin.

**Action:** the next release (0.4.0) must ship the corrected bundled
skill so auto-loaded-from-Central becomes the clean headline cell with no
caveat. The #408 gate makes 0.4.0's archetype clean by construction.

### Finding F3 — Standalone archetype apps run zero ITs (silent false green)

The archetype-scaffolded **standalone** app wires no
`maven-failsafe-plugin`, so `mvn verify` executes **zero** `*IT` classes
and still reports `BUILD SUCCESS`. CLAUDE.md and the bundled skill state
failsafe is "wired in the root pom and inherited by every module" — true
for tiko's *own* reactor, false for a generated standalone app, which has
no such parent. The agent-under-test's first declared-ready `mvn verify`
passed exit 0 while silently running none of the mandated integration
test; it took an explicit correction turn to add failsafe before the IT
ran at all. This is the single most consequential finding: it is a silent
trap on exactly the `Done` criterion ("`mvn verify` green" + an IT that
asserts a notification) that the prompt — and real users — depend on.

**Action:** the archetype pom should include `maven-failsafe-plugin`
(and bind `integration-test`/`verify`), or the skill must explicitly call
out that a standalone app needs failsafe wired before `*IT` runs. Doc
half is ARCH-13 (docs describe shipped reality — for *generated* apps,
not just the repo).

### Finding F4 — No documented test seam for FakeKafkaBroker; auto-started transport collides

`io.tiko.kafka.test.FakeKafkaBroker` clearly exists for in-process ITs,
but nothing documents how to make it the *active* transport, and the
generated `KafkaTransportBootstrap` works against the test:

- it hardcodes the real-client (2-arg) `KafkaBootstrapSupport`
  constructor and keeps its `sources()` / `sinks()` private, so the only
  way to drive the fake broker is to hand-rebuild a parallel
  `KafkaBootstrapSupport` mirroring the generated descriptors;
- it auto-starts via the `TransportBootstrap` ServiceLoader SPI inside
  `Tiko.create()`, pointing at an unreachable localhost broker, so the IT
  must *also actively suppress it* — the agent stripped
  `META-INF/services/io.tiko.TransportBootstrap` from `target/classes`
  via antrun and pointed failsafe's `classesDirectory` at that stripped
  dir (because the packaged jar still carried the SPI registration).

That is a lot of framework-internal reverse-engineering for what should
be a one-liner. Note this is the agent solving a *real* gap correctly —
but the cost (3 of its correction turns trace here, transitively) is the
finding.

**Action:** a documented "use the fake broker in a test" recipe, a
`TikoOptions` / property to disable transport autostart under test, or a
test-support helper that wires `FakeKafkaBroker` as the transport. Likely
a new issue; relates to the transport/SPI work (#117/#118).

### Finding F5 — Kafka config key-case doc contradiction

The bundled skill states Kafka config keys are camelCase-exact
(`bootstrapServers`); the shipped `tiko-kafka` `defaults.yaml` uses
kebab-case (`bootstrap-servers`). It did not bite run 1 (the agent used
defaults), but it is a live contradiction in agent-facing docs.

**Action:** reconcile the skill against `defaults.yaml` (ARCH-13
doc-coherence). Small skill/doc fix.

**Reading it honestly** (n=1 per cell — noise is large; ≥3 runs needed
before any aggregate):

- **The skill's marginal effect here was one rubric item.** With
  CLAUDE.md's reference present in *both* arms, the orchestrator-model
  essentials were already carried by CLAUDE.md; the SKILL.md's
  incremental teaching showed up only in the `@Produces` cookbook. A
  sharper signal would come from the **fresh-without floor** (no CLAUDE.md
  at all) — a distinct future cell.
- **Where the skill helped but the rubric didn't capture it:** with-skill
  got the `@KafkaSource` / `@KafkaSink` contract straight from the skill;
  no-skill reverse-engineered it from compiler errors + generated sources
  (a pre-ready compile iteration). Both reached correct usage, so the
  binary rubric shows no difference — but the skill saved a discovery
  loop. An effort/time benefit the 0/1 vector doesn't measure.
- **Where no-skill was arguably better:** it used repository **interfaces**
  (`ProductRepository` + an `H2…` impl, injected by interface), matching
  tiko's interfaces-over-impls house style, where with-skill used concrete
  repos; its first build was an **honest red** (IT ran and failed) where
  with-skill's was a **false green** (F3: IT silently didn't run); and it
  solved the F4 transport collision in **one** elegant turn (TCCL
  SPI-hiding) vs with-skill's two.
- **F4 dominated both runs regardless of the skill.** Neither doc covers
  driving `FakeKafkaBroker`, so both agents burned their hardest correction
  turns reverse-engineering the transport — reinforcing #414 as the
  highest-value DX fix this benchmark has surfaced.

**Bottom line:** on tiko's home turf with the baseline CLAUDE.md present,
the `tiko-build` skill moved the needle by one rubric item (the `@Produces`
cookbook) and saved one discovery loop (the `@KafkaSource` contract) — a
real but modest margin. The dominant friction (F4) and the structural
misses (T1 multi-module, H2 isolation) were skill-independent.

## Recording rules

- Each run is one row, appended at the bottom of the per-run table.
- `agent` column: write the precise model id, the date the run was
  performed (models silently snapshot-drift), and the skill-loading
  method, e.g. `claude-opus-4-7[1m] @ 2026-06-06 (SKILL.md auto-loaded
  via .ai-skills/)` or `gpt-5 @ 2026-06-06 (SKILL.md pasted into system
  prompt)`. The date matters; the same model id six months apart is
  not the same model.
- A "with-skill" run where the agent had access to the skill but did
  not actually read it counts as **without-skill** for analysis
  purposes — note this distinction in the transcript link and mark the
  cell `with-skill (not invoked)` so the per-cell aggregates stay
  honest.
- **Transcripts must outlast the share link.** Many agent UIs expose
  only ephemeral chat URLs. Before recording the transcript link,
  export the conversation to markdown and gist / commit it; link the
  permanent copy. A dead transcript link is worse than no link.
- **Source trees must be on a permanent URL.** Gist or branch — not a
  local path. A "source" column pointing at `C:\Users\...\run1` is
  meaningless to anyone else.
- Superseded runs: do not delete; add a follow-up row referencing the
  original run id in the transcript column.
- Failed runs (e.g. agent gave up, ran into a model error mid-run):
  record them. A failure is data.

### Counting correction turns

A correction turn is one round of *agent edits source code in response
to a build failure or test failure*. Specifically:

- ✅ Agent emits code → human runs `mvn verify` → it fails → human
  pastes the error → agent edits → repeat. Each agent edit is **one
  turn**.
- ✅ Agent edits code in response to its own self-noticed mistake
  before the human runs `mvn verify` — still one turn (intent is the
  same: "this code wasn't right").
- ❌ Conversational clarification ("did you mean X or Y?") is **not**
  a correction turn; record it in the transcript but don't count it.
- ❌ The initial code emission is turn 0, not turn 1.
- Cap: 5 turns. Anything past 5 is recorded as `>5` and the cell is
  marked **failed** regardless of whether `mvn verify` eventually
  passed. The cap exists so a benchmark cell doesn't degenerate into a
  pair-programming session.

### Rubric ambiguity handling

The rubric is 0/1 by design, but a few items have judgment-call edges
(notably T4 missing-reference, O3 event chain shape, and O4 invented
annotations). When a scorer is uncertain:
