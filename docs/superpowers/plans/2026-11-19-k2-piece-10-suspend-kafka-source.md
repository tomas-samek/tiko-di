# K2 Piece 10: `suspend` `@KafkaSource` Bridges Implementation Plan

> **For agentic workers:** this plan is executed in the session that wrote it, task by task, test first. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a `@KafkaSource` bridge may be a Kotlin `suspend fun`. Each record runs in a unit of
work of its own across the bridge's suspension points, its offset is committed after the bridge
has completed, and a failure takes the ingest-error path that exists. Closes #681.

**Architecture:** the consumer thread still handles one record at a time, and for a `suspend`
bridge it runs the bridge's coroutine itself: a small function in `tiko-coroutines`,
`SuspendBridges.run`, blocks the calling thread while the bridge runs in a unit of work
(`inEventScope`), publishes what the bridge returned inside that unit, and returns when the unit
has closed. The generated Kafka bootstrap calls it for a `suspend` source and tells the runner,
through the source's descriptor, that this source opens its unit itself. The runner then commits
as it does today. `tiko-kafka` stays free of Kotlin; `tiko-coroutines` learns nothing about
Kafka.

**Tech Stack:** kotlinx-coroutines 1.11.0 (`runBlocking`), `FakeKafkaBroker`, existing build.

**Spec:** issue #681; `docs/superpowers/specs/2026-11-04-kotlin-ksp-coroutines-design.md`, K2
item 6 ("Kafka") and its open point on the offset commit. Roadmap:
`docs/superpowers/plans/2026-11-18-kotlin-k2-coroutines-roadmap.md` (piece 10, decision D8).

## Decisions (owner, 2026-11-19: both as recommended)

| # | Question | Decided |
|---|---|---|
| D8 | When does a record of a `suspend` bridge count as done, and how does the consumer thread wait for it? | **When the bridge's coroutine has completed, the event it returned has been published to its synchronous handlers, and the unit of work has closed. Then the offset is committed, as for a regular bridge.** The consumer thread does not hand the record over and wait: it runs the coroutine itself (`runBlocking`), so the bridge's code runs on `tiko-kafka-consumer-<topic>` unless the bridge switches dispatcher, and synchronous handlers of the event run there as today. The alternative is to run the bridge on the container's coroutine threads and park the consumer thread; it adds a thread hop per record and gains nothing, because the consumer thread must not poll meanwhile either way. |
| D13 | `close()` begins while a `suspend` bridge is suspended. | **The bridge gets `tiko.kafka.shutdown-timeout` to finish, as a regular bridge does. After that it is cancelled, and the consumer thread exits.** The record stays uncommitted and is delivered again. The alternative is to cancel at once, which is faster and redelivers more often. |

## What follows, stated plainly

- **A bridge that switches dispatcher keeps its unit.** `withContext(Dispatchers.IO) { ... }`
  inside a `suspend` bridge sees the record's EVENT instances, because the unit travels with
  the coroutine (piece 3). A regular bridge has no way to do that.
- **A long suspension is a long time between polls**, as a slow regular bridge is:
  `max.poll.interval.ms` applies as today.
- **Cancelling at shutdown interrupts the consumer thread**, which is how a blocked
  `runBlocking` is cancelled. The runner does it only while a `suspend` bridge is in flight and
  treats that interrupt as the orderly stop it is, not as an ingest failure.
- **`@KafkaSink` stays as it is**: a `suspend` sink is still a compile error (#681, out of scope).

## Interfaces

- `tiko-coroutines`, called by generated code only:
  `SuspendBridges.run(container: Container, bridge: suspend () -> Any?)`. It blocks the calling
  thread, runs `bridge` in a unit of work of its own, publishes a non-null result on the
  container's event bus inside that unit, and returns once the unit has closed. What `bridge`
  or a synchronous handler throws is thrown to the caller after the unit has closed. An
  interrupt of the calling thread cancels the bridge and is thrown as `InterruptedException`.
- `tiko-kafka`: `GeneratedSourceDescriptor` gains `boolean opensItsUnit`; the seven-argument
  constructor stays, for bootstraps generated by an earlier processor.
- Generated bootstrap, for a `suspend` source:
  ```java
  private Object source0(Container container, Object payload, KafkaContext ctx) {
      SuspendBridges.run(container, __continuation ->
              container.get(Bridge.class).onPayment((Payment) payload, ctx, __continuation));
      return null;
  }
  ```

## What changed while implementing

- **The test program runs as the application's only module.** `KspProgram.run` loaded the whole
  test classpath, the compiled fixtures of `tiko-coroutines`' own tests included, which carry a
  container of their own. The program then booted as the second module of a multi-module
  application, and a multi-module boot found no module that owns `KafkaConfig`. `run` now leaves
  out a classpath directory that holds a Tiko container. Whether a real multi-module application
  with a Kafka bridge boots is a question of its own, outside this piece.
- **A cancelled bridge ends the runner's loop as an orderly stop.** The interrupt `stop()` sends
  reaches the runner as the bridge's `InterruptedException`, or as Kafka's `InterruptException`
  when it lands in the commit after the bridge returned; neither is reported as an ingest error
  once the runner is stopping. The consumer thread clears the interrupt before it closes its
  client. A cancelled bridge gets one second to run its cleanup.
- **The example's bridge writes to the ledger**, which is the suspending call, and returns
  `PaymentRecorded`; `PaymentHandler` keeps the `FirstDeliveryOnly` guard and turns a first
  delivery into a new `PaymentAccepted`, which the sink sends as the receipt.
- **`KotlinConstructRules.suspendUntilK2` went**: nothing else used it. The new rule is
  `suspendSource`, and both suspend rules share the "add the dependency" fix.
